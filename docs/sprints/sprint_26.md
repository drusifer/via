## Sprint 26 — CLI/Executor Refactoring & Query Performance (Tech Debt)

**Author**: Cypher (PM)
**Date**: 2026-06-20
**Theme**: Technical Debt & Quality — Refactor query executor/CLI parse routing, optimize chained relationship query performance, add JS body analyzer unit tests, and restore a clean test baseline.
**Points**: ~11pts

---

### Context

After shipping Sprint 25 (Dart/Flutter support) and resolving several query engine bugs, the project's backlog highlights key structural technical debt. 

Specifically:
1. **Monolithic Parse Routing**: The CLI execution flow in `via/main.py` and `via/core/executor.py` still relies on large argparse blocks and conditionals. Unifying this under a polymorphic handler registry will align the CLI/programmatic query execution paths.
2. **Chained Query Performance**: Composable chained relationship queries (using multiple `--via` or `--sans` stages) can cause inefficient database access patterns.
3. **JS Body Analyzer Test Coverage**: Although the `FunctionBodyAnalyzer` subclasses were successfully extracted, they lack dedicated unit tests in isolation.
4. **Baseline Failures**: 3 failing tests currently pollute the baseline suite.

---

### Sprint Goal

Resolve the technical debt items: refactor parser/executor routing, optimize complex chained queries, add unit test coverage for `_js_body` analyzers, and stabilize the test suite to a completely green baseline.

**Non-scope**: Adding new language support, implementing interactive TUI, or introducing new query CLI flags.

## Sprint 26 Architecture — CLI Parser & Executor Refactoring, Filter Optimization

**Author**: Morpheus (Tech Lead)
**Date**: 2026-06-20
**Status**: APPROVED

---

### 1. Unified Executor Registry and CLI Parser Replacement (S26-1)

#### Current Architecture & Smell
Currently, CLI arguments are parsed and dispatched in `via/__main__.py` using a monolithic `_dispatch_subcommand` block and `_run_pipeline_command`. The pipeline executor in `via/pipeline/executor.py` contains monolithic condition checks on `PipelineStage.stage_type`. 

#### Target Architecture
We will introduce a polymorphic registry pattern for executing pipeline stages and CLI commands.

1. **Stage Handler Registry**:
   Create a new module `via/pipeline/handlers.py` (or registry inside `via/pipeline/`) defining `StageHandlerABC` and registering concrete handlers:
   - `MatchStageHandler`
   - `RenderStageHandler`
   - `StatsStageHandler`
2. **Command Handler Registry**:
   Define `CommandHandlerABC` in `via/commands/base.py` and register handlers for CLI subcommands:
   - `IndexCommandHandler`
   - `StatsCommandHandler`
   - `McpCommandHandler`
   - `InstallCommandHandler`
   - `AskCommandHandler`
3. **Seam Alignment**:
   Ensure `ViaRunner` (the programmatic API) calls the same polymorphic stage handlers as the CLI, eliminating duplicate routing logic.

---

### 2. Performance Optimization for Chained Filters (S26-2)

#### Current Performance Bottleneck
When executing chained `--via` or `--sans` stages, the executor performs separate SQL queries for each stage, loading the intermediate symbol IDs into Python memory and performing sets intersection/difference. For large codebases, this results in multiple database calls (N+1 queries).

#### Design Decision: Query Batching & CTEs
We will optimize the database execution path in `DatabaseStore.query_relationships` and the executor stage pipeline:
1. **SQLite Common Table Expressions (CTEs)**:
   For chained relationship stages, compile the stages into a single nested SQLite query using CTEs (e.g., `WITH stage1 AS (...), stage2 AS (...) SELECT * FROM stage2`).
2. **Bulk Fetching**:
   If nested queries are not viable due to runtime post-filtering, optimize Python-side batching by executing `IN` queries with chunked symbol IDs rather than executing one query per symbol.

---

### 3. Dedicated Unit Tests for JS Body Analyzer (S26-3)

#### Technical Design
Create a new test file `tests/unit/test_js_body_analyzer.py`.
It will instantiate `_CallAnalyzer`, `_HttpCallAnalyzer`, and `_StringConstantAnalyzer` directly, passing mock tree-sitter AST nodes, to verify:
- Accurate extraction of call targets.
- HTTP path matching and extraction.
- Extraction of string constants from various JavaScript and TypeScript syntax structures.

---

### 4. Resolving Baseline Test Failures (S26-4)

#### Root Cause Analysis & Prescription

1. **Test**: `test_invalid_container_type_raises_error`
   - *Issue*: `_get_actual_inverted` in `PipelineExecutor` automatically normalizes/inverts query directions for `declares` relationships when the user provides mismatched types. This bypasses the validation that expects a `ValueError` when querying `method -V declares class`.
   - *Fix*: Modify `_get_actual_inverted` to enforce strict type checking. If the subject of `declares` is not a valid container type, raise `ValueError` instead of silently auto-inverting.

2. **Test**: `test_query_filepath_imports_filepath`
   - *Issue*: Import resolution between filepaths is failing to return matches.
   - *Fix*: Check the `imports` relationship generation inside `via/db/store.py` and `via/services/indexing.py`. Ensure that when a file imports a symbol from another file, a file-to-file `imports` relationship is correctly created in the `references` table.

3. **Test**: `test_sans_declares_returns_empty_markdown`
   - *Issue*: The query `via -mg '*.md' -tF --sans declares -mg '*' -tH` returns unexpected results.
   - *Fix*: Verify the relationship direction mapping for `declares` on markdown files. Ensure that if a markdown file has no headers, it is correctly returned, and files with headers are excluded.
